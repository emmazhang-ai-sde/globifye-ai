## 1. Goal

Danish's direction from the June 30 team meeting, quoted directly from the transcript:

> "We just need to test SIP... we are not just going to build an entire setup... take any SIP platform which you feel like from the list, and then test it out how it will integrate within our current setup for agent calling."

Scope is deliberately narrow: **prove the loop works**, not build a production system.

```
Audio in (via SIP) → transcribed → audio out (via SIP)
```

Explicitly **out of scope** for this MVP:
- Concurrency / multiple simultaneous calls (separate test item, not blocking this one)
- Production-grade error handling, reconnection logic, failover
- Full agent behavior (custom instructions, objection handling, etc.) — the LLM step can be a stub/passthrough for the first pass
- DID/number provisioning and billing (Abraham's pricing track, tracked separately)

## 3. Current Pipeline State (what SIP needs to plug into)

As of 6/30, the AI stack is tested but **not connected to any telephony layer**:

```
Modulate (STT) → Groq (LLM) → Deepgram Aura (TTS)
```

- Tested only through a basic Python script, no interface
- Hardcoded in Python using low-level queues/threads — not using LangChain (open question, tracked separately — see personal notes 7/1, item 2)
- No SIP integration attempted yet (confirmed 6/30: *"Have you tried to integrate SIP now?" "No, I haven't started on that."*)

## 4. Task Breakdown

Detailed step-by-step implementation guides (with concrete Asterisk/ARI config, references to existing pipeline code, and pitfalls): [`sip-loop-mvp-step-by-step-guidence/`](./sip-loop-mvp-step-by-step-guidence/)

### [Step 1 — Environment setup](./sip-loop-mvp-step-by-step-guidence/step1-environment-setup.md)
Get Asterisk running with ARI enabled (REST API + WebSocket event interface), and prove a single test call can be routed into it. This is new territory for the team — no prior telephony integration experience — so treat this as the highest-risk, most time-uncertain step. Likely friction points: NAT/networking config, codec compatibility, ARI Stasis application registration.

**Deliverable:** A test call (e.g., via a softphone client or free SIP trunk trial) successfully reaches Asterisk and triggers an ARI event.

### [Step 2 — Wire call audio into STT](./sip-loop-mvp-step-by-step-guidence/step2-wire-call-audio-into-stt.md)
Use Asterisk's external media / RTP forwarding (or ARI's recording/snoop channel features) to get the live call audio stream out of Asterisk and into the existing Modulate/Deepgram STT pipeline. The current pipeline consumes audio as a script input — this step requires adapting it to accept a live streamed source instead.

**Deliverable:** Words spoken on the test call show up as transcribed text in the existing pipeline's output.

### [Step 3 — Wire TTS output back into the call](./sip-loop-mvp-step-by-step-guidence/step3-wire-tts-output-into-call.md)
Take audio generated by the TTS step (Deepgram Aura) and play it back into the live call via ARI's playback API.

**Deliverable:** Audio generated by the pipeline is audible on the test call.

### [Step 4 — End-to-end MVP verification](./sip-loop-mvp-step-by-step-guidence/step4-end-to-end-mvp-verification.md)
One test call proving the full loop closes: call connects through Asterisk, speech is transcribed, the LLM replies, generated audio plays back into the call. **Passed 2026-07-07 (~1.8s turn latency) and shared with Danish as the "loop proven" checkpoint. This concludes the SIP loop MVP.**

### [Step 5 — PM demo console](./sip-loop-mvp-step-by-step-guidence/step5-pm-demo-ui.md)
Post-MVP: a standalone web console over the proven loop. Two synced interfaces (sales dashboard / client phone), multi-company routing with per-company knowledge base and voice, on-demand post-call analysis. Complete and verified (2026-07-10 to 07-13).

### [Step 6 — Supabase data sync](./sip-loop-mvp-step-by-step-guidence/step6-supabase-sync.md)
Calls, transcripts, and analyses synced into the merged backend project, reusing the ai-pipeline's own tables. Best-effort and off the hot path. **Live and verified (2026-07-13);** schema alignment log in [Step 6.1](./sip-loop-mvp-step-by-step-guidence/step6.1-schema-alignment-0713.md).

### [Step 7 — Agent roadmap and deferred scope](./sip-loop-mvp-step-by-step-guidence/step7-agent-roadmap.md)
Designs, not implementations: the knowledge base's RAG evolution (see the [RAG design doc](./rag-per-company-kb-design-doc.md)), AI/salesperson switching, and the full deferred-scope list (concurrency, streaming TTS, WebRTC, real auth, diarization, and more).

## 5. Open Questions / Risks

- **Ops burden of self-hosting Asterisk.** The rest of the stack (Next.js + Vercel) specifically avoided self-hosting a persistent server because Vercel can't hold long-lived WebSocket connections (see the Deepgram Option A/B decision). Asterisk reintroduces exactly that "need an always-on server somewhere" requirement, just at the SIP layer. Where does this server run? Not yet decided.
- **STT pipeline adaptation.** The current STT integration has only been tested against file/script input, not a continuous live RTP stream from Asterisk. Unknown how much rework this requires.
- **ARI vs. PJSIP re-evaluation.** If ARI's latency turns out to be a real problem once actually tested (not just on paper), may need to revisit PJSIP despite the higher implementation cost.
